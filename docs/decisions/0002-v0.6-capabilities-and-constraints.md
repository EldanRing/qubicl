# Qubicl 0.6: capable computers and explicit boundaries

Status: accepted and implemented for Qubicl 0.6. Candidate-specific
qualification results are recorded separately in signed release evidence.

## Context

Qubicl should support ordinary development, browsing, document work, and human
handoff. Several existing limits couple unrelated work to one interactive
lease, restrict applications to a fixed list, or require a whole release matrix
for a narrow change. Those mechanisms have user costs that exceed the boundaries
they protect. The [constraint register](../constraints.md) distinguishes real
security requirements from resource defaults, compatibility limits, and release
policy.

## Accepted behavior

| Area | 0.6 decision |
| --- | --- |
| Trust | One computer is a cooperative workspace. Protect the host, administrator credentials, and other computers. Do not claim hostile-code isolation between processes or clients inside one computer. No separate hardened mode is planned. |
| Ownership | Reserve exclusive ownership for interactive browser/desktop input. Observations, file work, and background tasks should not need GUI ownership. Keep practical adapters for existing tool inputs. |
| Tasks | Retain tasks by default across client disconnect and human takeover. Provide explicit stop and attachment controls. A runtime restart interrupts ordinary jobs; retain records and logs, restart declared services, and never automatically replay arbitrary jobs. |
| Human control | Control follows the connected viewer, with a visible, configurable reconnect grace period (10 seconds by default). Release after that grace; retain an authenticated operator recovery path. |
| Applications | Support installed applications, including user-installed applications, without a fixed product whitelist. Keep launch identity, resource use, and process ownership observable. |
| Browser | Provide a normal persistent browser for logins, extensions, downloads, and continued human use. Preserve Chromium's sandbox; remove unsafe launch defaults and arbitrary fixed tab/idle limits. Public extraction uses a separate anonymous context. |
| Network | New computers use the normal developer profile. Restricted and offline profiles remain explicit choices. Add scoped HTTP and TCP access with exact destinations or CIDRs, ports, and revocable grants. |
| Previews | Local app previews work automatically after publication. Remote access is guided and uses operator-managed DNS and certificates. Give apps isolated origins and normal app cookies. Owner publication follows the app; share credentials expire independently. |
| Devcontainers | Support guest lifecycle hooks and harmless metadata. Reject host hooks and privilege or host-mount expansion. Devcontainer feature plugins remain outside 0.6. |
| Dashboard | Routine saves are direct. Confirm destructive, interrupting, or authority-expanding actions and honor reauthentication grace. Local sign-in survives same-tab refresh using session storage, keeps existing idle/absolute expiry, and clears on logout or tab closure. No long-lived “remember me” mode. |
| Recovery | Keep backups manual. Improve verification, restore, clone, migration, and recovery without adding a scheduler or promising portable hard disk quotas. |
| Migration | Recoverably move 0.5 computers to the new defaults while preserving homes, IDs, credentials, and explicit user restrictions. Explain behavior changes before migration and retain a recovery path. |
| Platforms | Retain the existing CLI and dashboard support footprint. Do not add WSL dashboard, Intel macOS, or ARM support claims without separate qualification. |
| Release evidence | Select verification from changed inputs, artifacts, protocols, and platforms. Reuse applicable evidence with identity and freshness checks. Exercise all affected protocols, representative real clients, and additional clients whose adapters changed. Use physical hardware where the affected behavior requires it. |

## Consequences and acceptance

These decisions are implemented across runtime contracts, state migration,
adapters, the UI, and release tooling. Release qualification must still verify
their affected surfaces. Migration preserves explicit policies even when the
default changes. Computer credentials that permit arbitrary execution
still grant access to the shared workload; narrower tool scopes do not create
an internal hostile-code boundary.

Browser warnings must be resolved at the launch/security configuration, rather
than hidden. Task retention must remain distinct from interactive authority, so
retaining a job cannot allow queued old-owner input after takeover. Revoking a
preview or network grant must also close the connections it authorizes.

Release impact analysis must account for shared bundles, catalogs, state and
protocol contracts, image inputs, and dependency changes. A large 0.6 change can
still affect all six images. An npm-only or reused-image release is available
only once the builder, verifier, and publisher implement and validate that
boundary. Missing required real-client or hardware evidence remains outstanding;
source tests and copied historical results cannot stand in for it.

The initial representative client set is Codex and Open WebUI, with independent
MCP stdio, MCP HTTP, OpenAPI, and Open Terminal coverage. Add real client runs
when their adapter-specific behavior changes. Validate affected Linux, macOS,
and WSL workflows within the existing footprint, and physical phone behavior
when mobile interaction changes. Record required, reused, completed, and
unverified coverage separately.

Maintainer approval gates for commits, publication, expensive verification, and
live resources remain unchanged. They govern maintainers' actions and do not
determine confirmation dialogs inside the product.

Managed remote-access integrations, scheduled backups, notebooks, new platform
support, and devcontainer feature plugins are outside this release design.
