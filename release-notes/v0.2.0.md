# Qubicl 0.2.0

Qubicl 0.2.0 is a security, lifecycle, and client-compatibility release for
local AI computers. It keeps durable homes and the existing local-first model
while making upgrades, browser-profile handling, remote access, Open Terminal,
and release evidence substantially more explicit.

## Highlights

- `qubicl upgrade --all` previews exact image targets, acquisition estimates,
  preserved runtime states, and gateway-first execution before confirmation.
- Open Terminal adds bounded background processes, stdin, paged output, cleanup,
  and multi-file ZIP download. Open WebUI can display Qubicl-sanitized static
  HTML and SVG previews without enabling scripts, forms, refreshes, or external
  navigation; JavaScript and TypeScript are shown as source.
- `qubicl browser profile wipe COMPUTER` reports domains with stored cookies or
  site data, states exactly what is removed and preserved, and requires explicit
  confirmation. `browser_reset` remains API-compatible and is labeled **Reset
  tabs** because it does not clear the durable profile.
- Optional direct remote access uses the existing gateway container: local HTTP
  remains loopback-only, while an explicitly configured second listener provides
  TLS-only HTTPS/WSS with exact origin, network, host, SNI, rate, and per-computer
  authorization boundaries. It is off by default and never publishes computer
  containers directly.
- Viewer traffic now uses content-ID-bound image contracts and a gateway-derived
  internal credential. Raw VNC stays behind protected Unix sockets.
- Durable file operations and backup restoration now use descriptor-anchored,
  no-follow boundaries and validate complete archive graphs before promotion.
- Every v0.2 image candidate binds per-platform scan identity and OCI efficiency
  evidence, including compressed and expanded layer sharing and normalized
  package inventories from embedded SPDX attestations.

## Upgrade behavior

Install the v0.2 CLI and review the coordinated upgrade plan:

```sh
npm install -g qubicl-cli@0.2.0
qubicl upgrade --all
```

The upgrade preserves computer names, durable homes, browser profiles, resource
settings, and running, stopped, or absent runtime state. A pending lifecycle
journal rolls forward deterministically; it never falls back to deleting a
container selected only by a mutable name. During image replacement, the target
viewer contract comes from the exact acquired image while the retained old
runtime must still match the immutable source recorded in that journal.
Browser-capable runtimes prepare the durable Chromium profile and Downloads as
the unprivileged computer user; an empty root-owned directory left by a
prerelease runtime is repaired narrowly, while other ownership mismatches still
require the explicit `qubicl repair ownership` workflow.

State format 3 remains current. Existing v0.1 state is migrated in place under
the state lock. Legacy viewer images remain usable through their explicit legacy
contract, while the hardened viewer and optional remote gateway require matching
v0.2 image capabilities.

## Compatibility and validation profile

This release uses the pre-1.0 `initial` profile. Its signed schema-4 release
record requires the exact Linux x64 candidate, Codex and Open WebUI workflows,
all four protocol probes, native-Linux lifecycle evidence, and native-Linux
remote-access evidence. The broader `supported` profile additionally requires
the complete macOS, Windows/WSL 2, application, reboot, Docker Desktop/NAT, and
independent-review matrix. Qubicl does not claim that broader profile without
those records.

Local candidate preparation uses bounded two-job concurrency for BuildKit image
creation. Exact source/npm/native acceptance remains serial because those runs
share the Docker daemon, while isolated ports and temporary image tags prevent
cross-run residue. Shared-cache scans, OCI analysis, and final evidence
verification also remain serial.

Schema-3 v0.1 acceptance evidence remains verifiable for historical releases,
but it cannot authorize a v0.2 publication.

## Security and operator notes

- Remote access is absent unless an operator runs `qubicl gateway expose` and
  reviews a bind address, distinct port, certificate, private key, client
  networks, and exact HTTPS origins. All-interface and allow-all-client policies
  require separate consent. Qubicl does not configure the host firewall or DNS.
- Remote previews require an isolated wildcard preview domain covered by the
  configured certificate. Without it, local `.localhost` previews continue and
  remote preview URLs remain unavailable.
- Open Terminal's direct `/files/view` route downloads active file types. The
  Open WebUI compatibility path instead serves a self-contained,
  parser-normalized static document with a response-enforced sandbox through
  Open WebUI's existing file proxy; the browser does not need direct access to
  a Qubicl `.localhost` preview host. Scripted HTML remains paused by default
  and offers a separate five-minute **Run interactive preview** action. It runs
  the exact file snapshot already carried in the authenticated response, in
  place, so no second Open WebUI navigation or browser-visible credential is
  required. Use it only for trusted content: its unique-origin sandbox still
  blocks forms, frames, popups, downloads, and top navigation, but permitted
  scripts and external requests use the operator browser outside the
  computer's Qubicl network policy.
- Docker images and volumes are daemon-global resources. Cleanup previews them
  for manual review rather than claiming exclusive ownership and deleting them.
- Browser-profile inventory reports domains with stored cookies or site data;
  it does not inspect sensitive cookie values or claim that a domain represents
  stored authentication.
- Routine dependency review is manual and local. This repository does not
  configure Dependabot to create unsolicited public pull requests.

## Known limitations

- The optional direct TLS listener does not add a tunnel, sidecar, automatic
  certificate issuance, firewall automation, or a dashboard.
- Source and candidate tooling can enforce the initial release profile, but
  support claims remain limited to the post-freeze client and platform evidence
  actually signed with the release set.
- Very large backup archives, terminal output, or ZIP selections intentionally
  fail at documented resource bounds instead of consuming unbounded memory,
  storage, or controller time.
